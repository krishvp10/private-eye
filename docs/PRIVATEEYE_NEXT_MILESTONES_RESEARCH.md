# PrivateEye next milestones: official-source research

**Checked:** 2026-09-10  
**Scope:** vLLM, Qwen official model/API material, Playwright, and ONNX Runtime Web official documentation/source only.  
**Repository convention:** `private-eye-docs/` is the project documentation package; this note follows its existing Markdown convention and does not change source code.

## Executive findings

1. **The server path is viable, but should be treated as an image-first compatibility target.** Current vLLM online-serving documentation exposes an OpenAI-compatible Chat Completions endpoint at `/v1/chat/completions`, and its Chat API explicitly supports vision-related parameters. The Qwen2.5-VL vLLM recipe demonstrates serving Qwen2.5-VL-7B-Instruct and using `/v1/chat/completions` for benchmarking. However, vLLM's current supported-models page says the generic Transformers modeling backend for vision-language models currently accepts only image inputs; the Qwen2.5-VL recipe itself sets `--limit-mm-per-prompt '{"image":2,"video":0}'`. PrivateEye should therefore ship an image-only MVP contract and separately validate video before enabling it. [vLLM Online Serving — “OpenAI-Compatible Server”](https://docs.vllm.ai/en/latest/serving/online_serving/#openai-compatible-server); [vLLM OpenAI-Compatible Server — “Chat API”](https://docs.vllm.ai/en/latest/serving/online_serving/openai_compatible_server/#chat-api); [vLLM Qwen2.5-VL Usage Guide — “Qwen2.5-VL-7B-Instruct with DP=4”](https://docs.vllm.ai/projects/recipes/en/stable/Qwen/Qwen2.5-VL.html#qwen25-vl-7b-instruct-with-dp4); [vLLM Supported Models — “Transformers”](https://docs.vllm.ai/en/latest/models/supported_models/#transformers)

2. **Qwen2.5-VL has concrete preprocessing requirements that belong in the server deployment checklist.** The official model card recommends installing Transformers from source to avoid `KeyError: 'qwen2_5_vl'`, recommends `qwen-vl-utils[decord]==0.0.8` for visual-input handling, documents image input as local path/URL/base64, and exposes `min_pixels`/`max_pixels` controls. It also documents a default 32,768-token context configuration and optional FlashAttention 2 acceleration. [Qwen2.5-VL-7B-Instruct model card — “Requirements”, “Quickstart”, “More Usage Tips”, and “Processing Long Texts”](https://huggingface.co/Qwen/Qwen2.5-VL-7B-Instruct#requirements)

3. **Playwright now has a direct accessibility-tree-plus-geometry path.** `locator.ariaSnapshot()` is available from v1.49; `boxes: true` (v1.60) appends viewport-relative CSS-pixel boxes; `mode: "ai"` (v1.59) adds element references and iframe snapshots; `ariaSnapshotJSON()` is available from v1.63 and can return `box` fields. `locator.boundingBox()` remains the fallback/precise per-element API and returns `null` for invisible elements. [Playwright Locator API — `ariaSnapshot`, `ariaSnapshotJSON`, and `boundingBox`](https://playwright.dev/docs/api/class-locator#locator-aria-snapshot); [Playwright ARIA snapshots guide — “Using page.ariaSnapshot() and locator.ariaSnapshot()”](https://playwright.dev/docs/aria-snapshots#using-pageariasnapshot-and-locatorariasnapshot)

4. **ONNX Runtime WebGPU needs capability detection and a WASM fallback.** Official ORT Web docs mark WebGPU support as experimental, restrict documented browser support to Chromium-based combinations (with version notes), require a browser WebGPU implementation and suitable GPU/driver, disallow the WASM proxy worker with WebGPU, and limit graph capture to static shapes with all kernels on WebGPU. [ONNX Runtime Web — “Supported Versions”](https://onnxruntime.ai/docs/get-started/with-javascript/web.html#supported-versions); [Using the WebGPU Execution Provider — “What is WebGPU? Should I use it?”, “Graph Capture”, and “IO binding”](https://onnxruntime.ai/docs/tutorials/web/ep-webgpu.html); [The ‘env’ Flags and Session Options — `env.wasm.proxy` and `enableGraphCapture`](https://onnxruntime.ai/docs/tutorials/web/env-flags-and-session-options.html#envwasmproxy)

## 1. vLLM: current multimodal and OpenAI-compatible support for Qwen2.5-VL

### What is supported

- vLLM's current online-serving documentation lists an OpenAI-compatible Chat Completions API at `/v1/chat/completions`; the API is applicable to text-generation models with a chat template. [vLLM Online Serving — “OpenAI-Compatible Server”](https://docs.vllm.ai/en/latest/serving/online_serving/#openai-compatible-server)
- The detailed OpenAI-compatible-server page says its Chat API is compatible with OpenAI Chat Completions and explicitly supports vision- and audio-related parameters. It also notes that `image_url.detail` is not supported. [vLLM OpenAI-Compatible Server — “Chat API”](https://docs.vllm.ai/en/latest/serving/online_serving/openai_compatible_server/#chat-api)
- vLLM's multimodal-inputs guide says multimodal requests follow the model's Hugging Face format and supports image/video/audio modality-specific inputs. The guide warns that multimodal support is actively iterating. [vLLM Multimodal Inputs — overview and “Offline Inference”](https://docs.vllm.ai/en/latest/features/multimodal_inputs/#multimodal-inputs)
- The official Qwen2.5-VL recipe contains a current Qwen2.5-VL-7B-Instruct launch example using `vllm serve`, `--data-parallel-size 4`, and `--limit-mm-per-prompt '{"image":2,"video":0}'`; its benchmark client targets `/v1/chat/completions` with `--backend openai-chat`. [vLLM Qwen2.5-VL Usage Guide — “Qwen2.5-VL-7B-Instruct with DP=4” and “Qwen2.5VL-7B Benchmark on VisionArena-Chat Dataset”](https://docs.vllm.ai/projects/recipes/en/stable/Qwen/Qwen2.5-VL.html#qwen25-vl-7b-instruct-with-dp4)
- The same recipe says its Markdown guides are kept as a historical reference and points readers to `recipes.vllm.ai` for up-to-date interactive recipes. This is an uncertainty for release pinning: use the page as evidence that the model path exists, but verify the exact vLLM release and command in the deployment environment. [vLLM Qwen2.5-VL Usage Guide — page notice](https://docs.vllm.ai/projects/recipes/en/stable/Qwen/Qwen2.5-VL.html)

### Important constraints for PrivateEye

- The current supported-models page says the Transformers modeling backend supports vision-language models but “currently accept[s] only image inputs”; video support is described as future work. This makes image-only serving the safest current contract unless a native Qwen2.5-VL implementation and tested video path are confirmed for the pinned vLLM build. [vLLM Supported Models — “Transformers”](https://docs.vllm.ai/en/latest/models/supported_models/#transformers)
- vLLM recommends `--allowed-media-domains` to restrict remote media access and `VLLM_MEDIA_URL_ALLOW_REDIRECTS=0` to prevent redirects bypassing those restrictions. For a privacy-sensitive agent, prefer sanitized image bytes/data URLs or an allowlisted media origin rather than arbitrary page URLs. [vLLM Multimodal Inputs — security note](https://docs.vllm.ai/en/latest/features/multimodal_inputs/#multimodal-inputs)
- vLLM-specific generation controls can be passed through the OpenAI client’s `extra_body`; the OpenAI-compatible-server documentation shows this for structured outputs and other vLLM parameters. [vLLM OpenAI-Compatible Server — “Extra Parameters”](https://docs.vllm.ai/en/latest/serving/online_serving/openai_compatible_server/#extra-parameters)

### Suggested server milestone

**Milestone S1 — freeze and canary an image-only `/v1/chat/completions` contract.** Pin a tested vLLM build, serve `Qwen/Qwen2.5-VL-7B-Instruct`, send OpenAI-style text plus image content, set an explicit multimodal limit, and validate structured `AgentAction` output through vLLM's documented extra-parameter path. Do not make video a release criterion until a pinned-build test passes; this recommendation follows the current image-only Transformers-backend statement and the recipe's explicit `video: 0` limit. [vLLM Supported Models — “Transformers”](https://docs.vllm.ai/en/latest/models/supported_models/#transformers); [vLLM Qwen2.5-VL Usage Guide](https://docs.vllm.ai/projects/recipes/en/stable/Qwen/Qwen2.5-VL.html#qwen25-vl-7b-instruct-with-dp4)

## 2. Qwen2.5-VL: official model/API requirements

### Model and preprocessing requirements

- The official Qwen2.5-VL-7B-Instruct card identifies the model as an image-text-to-text multimodal model and documents three sizes in the family: 3B, 7B, and 72B. [Qwen2.5-VL-7B-Instruct model card — introduction](https://huggingface.co/Qwen/Qwen2.5-VL-7B-Instruct#introduction)
- The card says Qwen2.5-VL code is in the latest Hugging Face Transformers and advises building Transformers from source with `pip install git+https://github.com/huggingface/transformers accelerate`; otherwise users may encounter `KeyError: 'qwen2_5_vl'`. [Qwen2.5-VL-7B-Instruct model card — “Requirements”](https://huggingface.co/Qwen/Qwen2.5-VL-7B-Instruct#requirements)
- The card recommends `qwen-vl-utils[decord]==0.0.8` for convenient visual-input processing and says non-Linux users may need the torchvision fallback if `decord` is unavailable. [Qwen2.5-VL-7B-Instruct model card — “Quickstart”](https://huggingface.co/Qwen/Qwen2.5-VL-7B-Instruct#quickstart)
- The official Transformers example loads `Qwen2_5_VLForConditionalGeneration` with `torch_dtype="auto"` and `device_map="auto"`, then loads `AutoProcessor`. It presents FlashAttention 2 as an optional acceleration/memory-saving configuration, especially for multi-image and video scenarios. [Qwen2.5-VL-7B-Instruct model card — Transformers quickstart](https://huggingface.co/Qwen/Qwen2.5-VL-7B-Instruct#using--transformers-to-chat)
- The card documents image inputs as local files, HTTP(S) URLs, or base64 data URLs. It documents video inputs and notes that video URL compatibility depends on the reader/library combination; the table distinguishes torchvision and decord support. [Qwen2.5-VL-7B-Instruct model card — “More Usage Tips” and “Video inference”](https://huggingface.co/Qwen/Qwen2.5-VL-7B-Instruct#more-usage-tips)
- The default visual-token range is documented as 4–16,384 per image. The card recommends controlling cost and memory with `min_pixels`/`max_pixels`; it gives a 256–1,280 visual-token example and says exact resized dimensions are rounded to a multiple of 28. [Qwen2.5-VL-7B-Instruct model card — “Image Resolution for performance boost”](https://huggingface.co/Qwen/Qwen2.5-VL-7B-Instruct#image-resolution-for-performance-boost)
- The current model `config.json` is documented as supporting up to 32,768 tokens. The card describes YaRN for longer text, but warns that YaRN affects temporal and spatial localization and is not recommended for those tasks. [Qwen2.5-VL-7B-Instruct model card — “Processing Long Texts”](https://huggingface.co/Qwen/Qwen2.5-VL-7B-Instruct#processing-long-texts)

### API/deployment implications

- Qwen's official v2.5 deployment documentation describes vLLM as an OpenAI-compatible API service, defaulting to `http://localhost:8000`, with `/v1/chat/completions` and the OpenAI Python client. It advises passing sampling parameters because defaults may be unsuitable for Qwen2.5 models. [Qwen v2.5 documentation — “OpenAI-Compatible API Service”](https://qwen.readthedocs.io/en/v2.5/deployment/vllm.html#openai-compatible-api-service)
- The Qwen v2.5 deployment page documents structured/JSON output with vLLM and points to vLLM's `guided_json` support, while recommending that the required format also be stated in the prompt/system message. [Qwen v2.5 documentation — “Structured/JSON Output”](https://qwen.readthedocs.io/en/v2.5/deployment/vllm.html#structured-json-output)
- Qwen's generic v2.5 quickstart recommends Python 3.10+, PyTorch 2.3+, and Transformers 4.37+ for the Qwen2.5 text-model quickstart. These are generic Qwen2.5 documentation requirements, not a Qwen2.5-VL-specific compatibility guarantee; the VL card's source-build guidance should take precedence for this project. [Qwen v2.5 Quickstart — “Hugging Face Transformers & ModelScope”](https://qwen.readthedocs.io/en/v2.5/getting_started/quickstart.html#hugging-face-transformers-modelscope); [Qwen2.5-VL-7B-Instruct model card — “Requirements”](https://huggingface.co/Qwen/Qwen2.5-VL-7B-Instruct#requirements)

### Suggested model milestone

**Milestone S2 — reproduce the official Qwen preprocessing path before tuning prompts.** Build a clean environment, install the required Transformers source build and `qwen-vl-utils` variant, run one local-image request, then measure the selected `min_pixels`/`max_pixels` budget against latency and output quality. Keep the model's 32,768-token limit and the localization warning around YaRN in the deployment record. [Qwen2.5-VL-7B-Instruct model card — “Requirements”, “Quickstart”, “Image Resolution for performance boost”, and “Processing Long Texts”](https://huggingface.co/Qwen/Qwen2.5-VL-7B-Instruct#requirements)

## 3. Playwright: ARIA snapshots, locators, and geometry

### Current APIs

- `locator.ariaSnapshot()` captures the ARIA snapshot of an element/subtree and was added in Playwright v1.49. The default representation is YAML-like and describes roles, accessible names, attributes/states, and text. [Playwright Locator API — `locator.ariaSnapshot`](https://playwright.dev/docs/api/class-locator#locator-aria-snapshot)
- `ariaSnapshot({ mode: "ai" })` was added in v1.59. The AI mode includes element references, does not wait for a matching element, throws if none match, and includes snapshots of iframes inside the target. [Playwright Locator API — `ariaSnapshot` option `mode`](https://playwright.dev/docs/api/class-locator#locator-aria-snapshot-option-mode)
- `ariaSnapshot({ boxes: true })` was added in v1.60. It appends `[box=x,y,width,height]` for each element; coordinates are viewport-relative CSS pixels from `Element.getBoundingClientRect()`, and the default is `false`. [Playwright Locator API — `ariaSnapshot` option `boxes`](https://playwright.dev/docs/api/class-locator#locator-aria-snapshot-option-boxes)
- `locator.ariaSnapshotJSON()` was added in v1.63 and returns the same tree as JSON. Its documented nodes can include role, name, text, children, state flags, link URL/placeholder properties, AI refs/cursor, and a `box` when boxes are requested. [Playwright Locator API — `ariaSnapshotJSON`](https://playwright.dev/docs/api/class-locator#locator-aria-snapshot-json)
- `locator.boundingBox()` was added in v1.14 and returns `{x, y, width, height}` or `null` when the matched element is not visible. Coordinates are relative to the main-frame viewport; scrolling changes them and child-frame elements are reported relative to the main frame. [Playwright Locator API — `boundingBox`](https://playwright.dev/docs/api/class-locator#locator-bounding-box)
- Playwright recommends user-facing, explicit locators such as role and label locators. The locator guide says locators re-resolve an up-to-date DOM element before each action, which is useful for a browser agent operating across re-renders. [Playwright Locators guide — “Quick Guide” and “Locating elements”](https://playwright.dev/docs/locators#quick-guide)
- Playwright's ARIA-snapshot guide documents both `page.ariaSnapshot()` and `locator.ariaSnapshot()` for programmatic YAML snapshots. [Playwright ARIA snapshots — “Using page.ariaSnapshot() and locator.ariaSnapshot()”](https://playwright.dev/docs/aria-snapshots#using-pageariasnapshot-and-locatorariasnapshot)

### Suggested client milestone

**Milestone C1 — use a version-gated accessibility graph.** If the pinned Playwright is at least v1.60, prefer `ariaSnapshot({ boxes: true, mode: "ai" })`; if it is at least v1.63, evaluate `ariaSnapshotJSON()` as the structured transport. Retain per-locator `boundingBox()` as a fallback and treat `null`, negative coordinates, and scroll-sensitive coordinates as normal cases requiring visibility/scroll handling. This is a design recommendation derived from the documented API behavior. [Playwright Locator API — `ariaSnapshot`, `ariaSnapshotJSON`, and `boundingBox`](https://playwright.dev/docs/api/class-locator#locator-aria-snapshot)

## 4. ONNX Runtime Web: WebGPU constraints relevant to PrivateEye

### Browser and hardware constraints

- ONNX Runtime Web's getting-started page marks the WebGPU import as an experimental feature and requires importing `onnxruntime-web/webgpu` rather than the default package. [ONNX Runtime Web — “Import”](https://onnxruntime.ai/docs/get-started/with-javascript/web.html#import)
- The official support table lists WebGPU support for Chrome/Edge on Windows, Android, and macOS, but not iOS, Safari, or Firefox in the documented matrix. It states that Chromium v113+ is required on Windows, Chromium v121+ on Android, and Float16 requires Chrome v121+ or Edge v122+ on Windows. [ONNX Runtime Web — “Supported Versions”](https://onnxruntime.ai/docs/get-started/with-javascript/web.html#supported-versions)
- The WebGPU EP documentation says the underlying browser must implement WebGPU. Its native requirements table identifies the relevant Dawn backends: Direct3D 12/Vulkan on Windows, Vulkan on Linux/Android, and Metal on macOS/iOS. [ONNX Runtime WebGPU EP — “Requirements”](https://onnxruntime.ai/docs/execution-providers/WebGPU-ExecutionProvider.html#requirements)

### Runtime and performance constraints

- The ORT WebGPU tutorial says WebGPU is intended for more compute-intensive models, while lightweight models can continue using WASM for smaller binary size. [Using the WebGPU Execution Provider — “What is WebGPU? Should I use it?”](https://onnxruntime.ai/docs/tutorials/web/ep-webgpu.html#what-is-webgpu-should-i-use-it)
- The WASM proxy worker cannot work with the WebGPU execution provider because GPU buffers are not transferable. The same page documents a CSP limitation: the proxy worker uses a Blob to create a worker, which CSP may block. [ORT env/session options — `env.wasm.proxy`](https://onnxruntime.ai/docs/tutorials/web/env-flags-and-session-options.html#envwasmproxy)
- Graph capture is only appropriate when model shapes are static and all computing kernels run on WebGPU. ORT says models with dynamic shapes may need free-dimension overrides; some models will fail initialization with graph capture and must disable it. [ORT env/session options — `enableGraphCapture`](https://onnxruntime.ai/docs/tutorials/web/env-flags-and-session-options.html#enablegraphcapture); [Using the WebGPU Execution Provider — “Graph Capture”](https://onnxruntime.ai/docs/tutorials/web/ep-webgpu.html#graph-capture)
- By default, ORT copies inputs to GPU and outputs back to CPU. The WebGPU tutorial documents GPU-buffer IO binding (`Tensor.fromGpuBuffer`, preallocated outputs, and `preferredOutputLocation`) when PrivateEye wants to keep intermediate data on the GPU. [Using the WebGPU Execution Provider — “Keep tensor data on GPU (IO binding)”](https://onnxruntime.ai/docs/tutorials/web/ep-webgpu.html#keep-tensor-data-on-gpu-io-binding)

### Suggested browser milestone

**Milestone W1 — implement WebGPU capability gating and WASM fallback.** Detect the documented browser/platform support, import the WebGPU bundle only when available, avoid the WASM proxy-worker setting for WebGPU, start with graph capture disabled unless model shapes and kernel placement are verified, and use GPU-buffer IO binding only after measuring transfer costs. This recommendation follows the ORT support matrix and runtime constraints above. [ONNX Runtime Web — “Supported Versions”](https://onnxruntime.ai/docs/get-started/with-javascript/web.html#supported-versions); [ORT env/session options](https://onnxruntime.ai/docs/tutorials/web/env-flags-and-session-options.html#envwasmproxy); [Using the WebGPU Execution Provider](https://onnxruntime.ai/docs/tutorials/web/ep-webgpu.html)

## Gaps and uncertainties

- **Exact vLLM release pin:** the official Qwen2.5-VL recipe is labeled a historical Markdown reference and directs readers to `recipes.vllm.ai`; this note does not assert a specific vLLM version. [vLLM Qwen2.5-VL Usage Guide — page notice](https://docs.vllm.ai/projects/recipes/en/stable/Qwen/Qwen2.5-VL.html)
- **Video support path:** current vLLM documentation's generic Transformers backend says vision-language inputs are image-only, while Qwen's own model card documents video processing. Native-vLLM versus Transformers-backend behavior must be tested with the exact model/runtime combination before PrivateEye enables video. [vLLM Supported Models](https://docs.vllm.ai/en/latest/models/supported_models/#transformers); [Qwen2.5-VL model card](https://huggingface.co/Qwen/Qwen2.5-VL-7B-Instruct#video-inference)
- **Hardware sizing:** the cited official Qwen2.5-VL card and vLLM recipe document model/runtime commands and memory-related controls, but this research does not claim a universal VRAM requirement or latency target. Those values should be measured on PrivateEye's intended GPU and quantization choice. [Qwen2.5-VL model card](https://huggingface.co/Qwen/Qwen2.5-VL-7B-Instruct); [vLLM Qwen2.5-VL Usage Guide](https://docs.vllm.ai/projects/recipes/en/stable/Qwen/Qwen2.5-VL.html)
- **Playwright version availability:** the API reference records the version in which each feature was added; the repository must compare those versions with its actual pinned package before adopting the newer snapshot options. [Playwright Locator API](https://playwright.dev/docs/api/class-locator#locator-aria-snapshot)
- **ORT operator/model coverage:** this note deliberately does not claim that every ONNX operator or model is WebGPU-compatible. PrivateEye should run its actual redaction model through the target ORT WebGPU build and retain a WASM fallback when initialization or execution fails. [ONNX Runtime Web — “Supported Versions”](https://onnxruntime.ai/docs/get-started/with-javascript/web.html#supported-versions); [Using the WebGPU Execution Provider](https://onnxruntime.ai/docs/tutorials/web/ep-webgpu.html)
